## Clarifications

### Session 2026-11-02

- Q: Where must the "untagged endpoint is an error" rule be enforced? → A:
  Enforcement is test-suite-only — the cross-cutting sweep test (CI) is the
  sole guard; no fail-fast startup guard is added (simplicity/YAGNI).
- Q: In the display order, where does the infrastructure tag (`Health`) go?
  → A: Last — the 10 domain tags in canonical order (`Auth`, `Employees`,
  `Tourists`, …, `Chatbot`) followed by `Health` at the end.
- Q: How is the tag registry kept aligned with the canonical domain module
  list? → A: The registry is an explicit, hand-written catalog (names +
  descriptions), not mechanically derived; a test verifies 1:1 alignment
  with the canonical domain module list.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every endpoint appears under exactly one declared tag (Priority: P1)

A developer (or an agent) opening the generated API documentation of
PassaNorte sees every operation grouped under a meaningful, English-named
tag that matches its domain module — `Auth`, `Employees`, `Tourists`,
`Tourist Spots`, etc. No operation falls back into a default, uncategorized
group, and no operation carries a tag that was invented ad hoc in a module.

**Why this priority**: This is the core guarantee — without it the
documentation is unusable and the contract for the two frontends (React
panel, Kotlin Passaporte app) cannot be reliably split per module.

**Independent Test**: A cross-cutting test sweeps the generated OpenAPI
document and fails when any operation (a) declares no tag, (b) falls back
to the default tag, or (c) declares a tag absent from the central registry.

**Acceptance Scenarios**:

1. **Given** the OpenAPI document generated by the running application,
   **When** every operation declared in it is inspected, **Then** each one
   belongs to exactly one tag of the central registry (exactly one tag per
   operation — no operation exposes two or more registry tags).
2. **Given** the sweep of all operations, **When** any operation is missing
   an explicit tag or carries an unregistered tag, **Then** the sweep fails
   and reports the offending path + method, and no build proceeds.
3. **Given** the documented endpoints of the already-shipped modules
   (auth, employees, tourists, health), **When** the documentation is
   inspected, **Then** each of their operations carries the correct
   registry tag (auth → `Auth`, employees → `Employees`, tourists →
   `Tourists`, health → the infrastructure tag).

---

### User Story 2 - Tag catalog is defined once, in the shared core (Priority: P2)

A developer adding a seventh domain module (or documenting a new
infrastructure concern) touches a single, central place that defines all
allowed tags — name, description and display order — instead of sprinkling
tag strings across routers. Consumers of the documentation see the tags in
a stable, deliberate order (domain modules and the infrastructure entry),
not the accidental order in which routers happen to be registered.

**Why this priority**: This is the single-source-of-truth property the
modular monolith constitution requires; it keeps the tag list an
infrastructure concern owned by `core/`, mirroring the canonical
`DOMAIN_MODULES` list.

**Independent Test**: Inspecting the application configuration shows a
declared tag catalog (name + description + display order) derived from /
aligned with the canonical domain module list, and any tag used anywhere in
the code resolves to an entry of that catalog.

**Acceptance Scenarios**:

1. **Given** the running application, **When** the documentation is read,
   **Then** it declares each registry tag once with a name, a description,
   and they appear in the intended display order: the 10 domain tags in
   canonical order, with the infrastructure tag (`Health`) last.
2. **Given** a module router file, **When** its endpoints are inspected,
   **Then** each references the central registry's tag by constant/
   imported value — there is no raw, loose tag string typed inline in
   module code.
3. **Given** an endpoint that uses a tag which does not match any
   registered tag (typo or invented label), **When** the cross-cutting
   sweep runs, **Then** it fails.

---

### User Story 3 - Documentation grouping matches module boundaries (Priority: P3)

A reviewer comparing the API documentation to the modular-monolith
boundaries verifies that the operations of each domain module appear
grouped under exactly that module's tag — auth operations under `Auth`,
employee operations under `Employees`, tourist operations under `Tourists`
— so the documentation is a faithful map of the bounded contexts.

**Why this priority**: The documentation must reflect the constitution's
domain split so a future microservice extraction can be planned straight
off the docs; but it is a consequence of stories 1–2 already being
correct.

**Independent Test**: For each shipped domain module, the group of
operations shown under its tag in the documentation is exactly the set of
that module's endpoints (no foreign operation leaks into the group, none
of the module's operations land in another group).

**Acceptance Scenarios**:

1. **Given** a domain module's endpoints, **When** the documentation is
   inspected, **Then** every operation of that module is grouped under
   that module's tag and only that tag.
2. **Given** two modules (e.g. `auth` and `employees`), **When** their
   documented tags are compared, **Then** no operation is shared between
   the groups (each path+method appears under exactly one domain tag).

---

### Edge Cases

- What happens when a module endpoint's path prefix does not obviously
  match its domain (e.g. shared health route, or a route registered by
  `core/` itself)? → It must still declare a tag; the tag for
  non-domain endpoints is the infrastructure tag (`Health`). The sweep
  treats core-registered and module-registered routes identically.
- What happens when a developer adds a new endpoint and forgets the tag?
  → The application must treat an untagged operation as an error: the
  cross-cutting sweep fails loudly at test time rather than letting the
  operation fall into the default documentation group.
- What happens when two tags are declared on the same operation
  (multi-tag list)? → The sweep must reject it: each operation carries
  exactly one registry tag, keeping every operation in one group only.
- What happens when the canonical module list gains a new domain? → The
  registry gains the corresponding tag in the same change (tag existence
  is required by, and checked against, the canonical domain list).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST declare a single, central registry of
  documentation tags in the shared infrastructure layer (`core/`),
  containing for each tag its name, description and display order — the
  sole source of truth, with no loose tag strings hardcoded in domain
  modules.
- **FR-002**: The registry MUST contain one tag per canonical domain
  module with the canonical English names `Auth`, `Employees`, `Tourists`,
  `Tourist Spots`, `Events`, `Gamification`, `Visitation`, `Dashboard`,
  `Notifications`, `Chatbot`, plus an infrastructure tag for the health
  endpoint — and MUST NOT contain any other tag. The registry is an
  explicit, hand-written catalog (not mechanically derived from the
  canonical module list); a cross-cutting test MUST verify its 1:1
  alignment with that list (every canonical module has exactly one tag,
  and no tag exists without a canonical module — except the one
  infrastructure tag).
- **FR-003**: Every API endpoint MUST declare its tag explicitly, and the
  declaration MUST reference the central registry (by exported constant /
  named value), never by an inline string literal in module code.
- **FR-004**: An untagged operation MUST be treated as an error by the
  project's verification suite: the cross-cutting test MUST fail and
  report the offending path + method when any operation lacks an explicit
  tag, uses only the default tag, or uses a tag outside the registry.
  Enforcement is test-suite-only — no runtime/startup guard is required
  (the CI sweep is the sole guard).
- **FR-005**: Each operation MUST carry exactly one registry tag —
  multi-tag operations MUST be rejected by the cross-cutting test.
- **FR-006**: The generated API documentation MUST include every registry
  tag with its description and in the configured display order — the 10
  domain tags in canonical order (`Auth`, `Employees`, `Tourists`,
  `Tourist Spots`, `Events`, `Gamification`, `Visitation`, `Dashboard`,
  `Notifications`, `Chatbot`) followed by the infrastructure tag (`Health`)
  last — so groups render consistently for documentation consumers.
- **FR-007**: All previously existing endpoints (auth, employees,
  tourists, health) MUST be migrated to declare their registry tag, and
  existing contract tests MUST be updated/extended to assert the tagging
  contract without weakening any pre-existing assertion.
- **FR-008**: The change MUST NOT alter route paths, HTTP methods, request
  or response payloads (including the camelCase JSON contract of spec
  005), status codes, or any business logic — only documentation metadata
  is added.
- **FR-009**: Tag names in the registry MUST follow the English-only code
  naming rule established by the project constitution (VII), mirroring the
  canonical domain module names; user-facing descriptions MAY be written
  to best serve API consumers of the two frontends.

### Key Entities *(include if feature involves data)*

- **Tag Registry Entry** — a documentation category with a canonical
  English name, a description, a display-order position; exactly one per
  canonical domain module plus one infrastructure entry for health.
- **API Operation** — a documented endpoint (path + method) that must
  reference exactly one registry entry via the module's router
  declaration.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the operations in the generated documentation carry
  an explicit, registered tag; zero operations fall under a default or
  uncategorized group.
- **SC-002**: 100% of operations carry exactly one tag (no multi-tag
  operations).
- **SC-003**: The tag catalog rendered in the documentation is identical
  in name (and order) to the central registry — 0 unregistered tags
  appear anywhere.
- **SC-004**: The cross-cutting sweep test, when run against a codebase
  where any endpoint loses its tag, fails within one test run and names
  the offending endpoint (demonstrating the guard is real, not vacuous).
- **SC-005**: Domain groupings in the documentation map 1:1 onto the
  bounded contexts: for each shipped domain module, all of its operations
  are under its tag and none of them appear under another module's tag.
- **SC-006**: Existing contract/integration tests for auth, employees,
  tourists and health all pass unmodified in behavior (no response
  payload, path or status change), updated only where they assert
  documentation metadata.

## Assumptions

- The canonical domain module list already exists as a single source of
  truth in `core/` (constitution, preamble rule 2); the tag registry stays
  aligned with it (verified by a cross-cutting test) while remaining an
  explicit catalog with its own hand-written descriptions.
- Tag descriptions are developer-facing documentation content and are
  therefore written in English, consistent with the constitution's naming
  rule; they are descriptive (what the group covers), not marketing text.
- The health endpoint remains the only non-domain, infrastructure
  endpoint in scope today; future core-owned shared endpoints (e.g.
  future versioning/ping routes) will reuse the infrastructure tag unless
  a new one is formally added to the registry.
- New domain modules (tourist_spots, events, gamification, visitation,
  dashboard, notifications, chatbot) have no endpoints yet; their tags are
  registered now so the convention is ready when those modules ship, but
  no code for them is written in this feature.
- The existing route prefixes/paths remain untouched; tagging is done at
  the router/operation declaration level without moving or renaming any
  route.
